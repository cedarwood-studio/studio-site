What we check

Every pipeline — adapted to your languages, your test runner, your stack — is checked against the same internal list, organized by what it's checking rather than how. See the proof repo for a working example of the kind of harness this builds; the checklist itself isn't published, but these are the categories every engagement runs through, scoped to the proof the job actually needs.

Pipeline structure

Triggers, concurrency handling, dependency caching, matrix strategy, a single merge-gating job.

Correctness gates

Lint, typecheck, unit/integration/regression tests, a negotiated coverage floor, a stated flaky-test policy.

Security

Secret scanning, dependency vulnerability scanning, SAST/static analysis, container scanning, least-privilege permissions, pinned actions.

Supply chain

Lockfile discipline, automated dependency updates, provenance/attestations where cheap.

Deploy safety

Environments and reviewers, a named rollback path, no production credentials from us.

Observability

Status badges, run summaries, artifact retention.

Maintainability

A handoff doc, clear naming, one gate a branch-protection rule can point at.

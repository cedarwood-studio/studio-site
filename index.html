What we do

Three kinds of work

Each one is scoped to your repository and your stack. There is no standard package, and nothing here is a product we install on top of your system.

Delivery pipelines

A build-and-release pipeline for a codebase that doesn’t have one, or a repair for one nobody trusts. Triggers, caching, a matrix where it earns its keep, and a single merge-gating job that a branch-protection rule can point at.

What you get
Workflows in your repository, under your review, with least-privilege permissions and pinned actions. Lint, typecheck, and your test suite running on a real service, not a mock. A handoff document that explains every gate and how to change it.
Proof of done
A green pipeline on your repository, gating merges, with the run history in front of you. We also show you a red one: a deliberate failure that proves the gate stops what it claims to stop.

Platform and cloud engineering

Kubernetes, managed cloud services, and the infrastructure code that describes them. Migrations off a hand-built environment, a rollback path that someone has actually walked, and the secrets handling that should have come first.

What you get
Infrastructure as code (Terraform, Pulumi, or Helm, to match what you already run), with environments, reviewers, and a named rollback path. No production credentials held on our side, on any engagement.
Proof of done
Infrastructure that passes its own checks: a clean plan with no drift, the policy and scanning gates green, and a post-deploy check against the live environment rather than against the build that produced it.

AI pipelines, built from scratch

A greenfield pipeline around a model (retrieval, tool use, structured extraction, or a batch scoring job), designed from the start around the thing that makes it a system rather than a demo: a way to tell whether it got better or worse.

What you get
The pipeline, a graded set of cases drawn from your real inputs, and a scoring harness that runs in CI against that set. Prompts and model versions in version control, so a change in behaviour has a commit attached to it.
Proof of done
An eval suite with a regression threshold the build enforces, and a scored baseline you can compare every later change against.

How we work

Estimate first, in five steps

  1. An estimate within a dayYou send the repository or a description of the system. We come back with a scope, a price, and the two or three things that would move the number most. It is written the way a technical spike is: from evidence rather than a guess.
  2. Fixed scope and fixed priceAgreed in writing before anything starts. No hourly billing, no published rate card, no estimate that quietly becomes a range.
  3. The milestone is fundedMoney goes into escrow against a defined milestone. Work begins after that, and the funding gate is what makes the delivery claim worth anything.
  4. Delivery, machine-verified and human-reviewedEvery change goes through the gates below before it reaches you, and a senior engineer reviews what comes out of them.
  5. HandoffA written operating document, the gates explained, and a repository your own team can keep without us. Nothing in the delivery depends on our staying involved.

What we check

Eight categories, every engagement

Every harness we write is cross-checked against the same internal list, scoped to the proof the job actually needs. The list itself is a working document and keeps changing. The categories are published, and these are they.

Pipeline structure

Triggers, concurrency, caching, matrix strategy, one merge-gating job.

Correctness gates

Lint, typecheck, unit and integration tests, a negotiated coverage floor, a stated flaky-test policy, migration-apply verification.

Security

Secret scanning, dependency vulnerability scanning, static analysis, container scanning, least-privilege permissions, pinned actions.

Supply chain

Lockfile discipline, automated dependency updates, provenance where it is cheap, behavioural malicious-package scanning, a minimum-release-age floor.

Deploy safety

Environments and reviewers, a named rollback path, and no production credentials held by us.

Deploy verification

Post-deploy checks against the live artifact, and real-browser checks against a deployed preview.

Observability

Status badges, run summaries, artifact retention, and declared schedules reconciled against real run history.

Maintainability

A handoff document, clear naming, and one gate a branch-protection rule can point at.

Greenfield web application

Replacing a WordPress reservation site with an application the client can maintain alone

A family trust’s private reservation site (booking a shared lake house, browsing photos, storing board documents) ran on WordPress, with an outside plugin vendor in the loop for anything past a content edit. That dependency was the friction. The brief was a clean replacement on a stack one person could operate.

The rebuild opened with a dated technical spike rather than a leap: stand up the target stack end to end (CMS backend, Postgres, file storage, transactional email, all deploying from GitHub) and prove authentication, uploads, and the data model before committing to a plan. The spike produced the estimate, and named the WordPress data migration and a media-privacy decision as the two largest sources of variance.

Every change since ships through one required gate: lint, typecheck, and a schema-migration-drift check ahead of the full suite, run against a real database rather than a mock. A behavioural dependency scanner catches malicious and typosquatted packages, not only known CVEs. A separate required check runs against the live deployed site, because a green build and a working deploy are not the same claim.

Prior engagement, same client

The WordPress booking system, and the case that replaced it

Before the rebuild, the same client ran its reservations on WordPress: a working booking calendar, delivered and in daily use by a private membership rather than the public. It did the job for years.

What ended it was not a failure but two compounding costs. Any structural change meant a round trip through an outside plugin vendor. And the stack had grown past what the client’s eventual single maintainer could safely operate alone. WordPress’s own template and plugin layering was later assessed, while scoping the replacement, at roughly double the effort per task compared with the stack that replaced it. The decision to rebuild was made against a measured number, on a system we had operated ourselves, rather than against a preference for newer tools.
